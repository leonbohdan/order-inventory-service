## 🧩 Блок 1: Алгоритмічний розігрів — індексація in-memory (TS/JS)

Перед роботою з PostgreSQL було змодельовано роботу індексу в оперативній пам'яті на TypeScript для пошуку товарів за трьома критеріями:
1. `category` (точний збіг `=`);
2. `inStock` (точний збіг `=`);
3. `price` (діапазонний пошук `minPrice <= price <= maxPrice`).

```
1. Linear Search O(N)               2. Index + findIndex O(K)           3. Index + Binary Search O(log K)
   [ Прохід по всіх 50k ]              Map.get("cat:inStock")              Map.get("cat:inStock")
   ┌────────────────────┐              ┌──────────────────────┐             ┌──────────────────────┐
   │ p1, p2, p3 ... pN  │              │ Бакет ~7k елементів  │             │ Бакет ~7k елементів  │
   │ (filter по кожному)│              │ (послідовний пошук)  │             │ (відсортований!)     │
   └────────────────────┘              └──────────────────────┘             └──────────┬───────────┘
   O(N) перевірок                      O(1) + O(K) перевірок                findLowerBound / findUpperBound
                                                                            O(1) + O(log K) перевірок!
```

### Результати бенчмарку (50 000 об'єктів, 1 000 запитів):

| Метод пошуку | Складність алгоритму | Час (1 000 запитів) | Затримка 1 запиту (avg) | Прискорення | Аналог у PostgreSQL |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **1. Лінійний пошук (`filter`)** | $\mathcal{O}(N)$ | **637.26 мс** | ~0.637 мс | Базовий ($1\times$) | **`Seq Scan`** (повне читання таблиці) |
| **2. Хеш-мапа + `findIndex`** | $\mathcal{O}(K)$ | **30.19 мс** | ~0.030 мс | **~21.1×** | Індекс на префікс + фільтр у пам'яті |
| **3. Хеш-мапа + Бінарний пошук** | $\mathcal{O}(\log K)$ | **3.58 мс** | **~0.0035 мс** | **~178×** | **B-Tree Index Scan** (Seek + Leaf Range Scan) |

> [!TIP]
> **Висновки розігріву:**  
> 1. Впорядкованість даних у бакетах дозволяє замінити лінійний перебір бінарним пошуком, скорочуючи час виконання у **178 разів**.
> 2. Реляційні бази використовують **B-Tree** як індекс за замовчуванням саме тому, що він підтримує відсортований стан даних і дозволяє шукати діапазони за $\mathcal{O}(\log N + K)$.

## 🐘 Блок 2: Генерація 200 000+ записів та анатомія вихідного запиту без індексів

### 1. Наповнення бази даних тестовим обсягом
Утилітою `psql` у таблицю `Order` було згенеровано 200 000 транзакцій із рівномірним випадковим розподілом 4 статусів (`PENDING`, `PAID`, `SHIPPED`, `CANCELLED`), сум замовлень і дат за останні 90 днів:

```sql
WITH u AS (SELECT array_agg(id) AS ids FROM "User")
INSERT INTO "Order" ("id", "userId", "status", "totalAmount", "createdAt")
SELECT
  gen_random_uuid(),
  u.ids[floor(random() * array_length(u.ids, 1) + 1)],
  (ARRAY['PENDING', 'PAID', 'SHIPPED', 'CANCELLED'])[floor(random() * 4 + 1)],
  floor(random() * 10000 + 100)::int,
  NOW() - (random() * (interval '90 days'))
FROM u, generate_series(1, 200000);
```

#### Фізичні метрики таблиці:
* **Кількість записів:** `200 006`
* **Розмір даних (Heap relation):** `26 MB`
* **Загальний розмір (разом із первинним ключем `Order_pkey`):** `41 MB`
* *Після наповнення виконано `ANALYZE "Order";` для оновлення статистики планувальника.*

---

### 2. Аналіз вихідного запиту без індексів (Baseline)

Цільовий аналітичний запит замовлень за останній тиждень:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM "Order"
WHERE "status" = 'PAID' AND "createdAt" >= NOW() - INTERVAL '7 days'
ORDER BY "createdAt" DESC;
```

#### Фактичний план виконання PostgreSQL:
```text
Sort  (cost=7505.88..7515.67 rows=3917 width=94) (actual time=30.853..31.820 rows=3868 loops=1)
  Sort Key: "createdAt" DESC
  Sort Method: quicksort  Memory: 520kB
  Buffers: shared hit=3275
  ->  Seq Scan on "Order"  (cost=0.00..7272.12 rows=3917 width=94) (actual time=0.040..29.030 rows=3868 loops=1)
        Filter: ((status = 'PAID'::text) AND ("createdAt" >= (now() - '7 days'::interval)))
        Rows Removed by Filter: 196138
        Buffers: shared hit=3272
Planning Time: 0.821 ms
Execution Time: 32.589 ms
```

#### 🔬 Анатомія плану без індексу:
1. **`Seq Scan on "Order"`:** Оскільки немає відповідного індексу, PostgreSQL читає всі 8 KB блоки таблиці поспіль від початку до кінця.
2. **`Buffers: shared hit=3272`:** База підняла в буферний кеш **3 272 сторінки** ($3272 \times 8\text{ KB} \approx 26.17\text{ MB}$) — тобто вичитала 100% фізичного обсягу таблиці.
3. **`Rows Removed by Filter: 196138`:** Колосальне навантаження на CPU: процесор перевірив і відкинув **196 тисяч записів**, щоб знайти лише 3 868 потрібних.
4. **Вузол `Sort (quicksort Memory: 520kB)`:** Оскільки таблиця на диску не зберігає впорядкованості за датою, база витратила додатковий час і півмегабайта RAM на сортування замовлень.
5. **`Execution Time: 32.59 ms`** (базова точка відліку).

## ⚡ Блок 3: Проєктування складеного індексу (Composite Index) в Prisma

### 1. Зміна схеми [schema.prisma](file:///home/bohdan/MyProjects/test_projects/order-inventory-service/server/prisma/schema.prisma)
У моделі `Order` було додано складений індекс на дві колонки:
```prisma
model Order {
  id          String      @id @default(uuid())
  userId      String
  status      String
  totalAmount Decimal     @default(0)
  createdAt   DateTime    @default(now())
  items       OrderItem[]
  user        User        @relation(fields: [userId], references: [id])

  @@index([status, createdAt])
}
```

### 2. Застосування міграції
Командою `npx prisma migrate dev --name add_order_composite_index` згенеровано міграцію:
```sql
-- CreateIndex
CREATE INDEX "Order_status_createdAt_idx" ON "Order"("status", "createdAt");
```

---

### 3. Аналіз запиту зі складеним індексом

#### Запит без LIMIT:
```text
Sort  (cost=3859.98..3869.76 rows=3912 width=94) (actual time=6.499..7.894 rows=3862 loops=1)
  Sort Key: "createdAt" DESC
  Sort Method: quicksort  Memory: 519kB
  Buffers: shared hit=2245
  ->  Bitmap Heap Scan on "Order"  (cost=108.52..3626.56 rows=3912 width=94) (actual time=0.850..4.716 rows=3862 loops=1)
        Heap Blocks: exact=2221
        Buffers: shared hit=2242
        ->  Bitmap Index Scan on "Order_status_createdAt_idx"  (actual time=0.564..0.566 rows=3862 loops=1)
              Index Cond: ((status = 'PAID'::text) AND ("createdAt" >= (now() - '7 days'::interval)))
              Buffers: shared hit=21
Execution Time: 8.968 ms
```

* **Чому це в 3.6 рази швидше?** Для пошуку адрес 3 862 рядків в індексі PostgreSQL прочитав лише **21 сторінку (168 KB)** замість 3 272 сторінок таблиці!
* **Чому з'явився `Bitmap Index Scan` і `quicksort`?** Запит повертає велику вибірку (3 862 рядки без `LIMIT`). Щоб уникнути випадкового стрибання по диску (Random I/O), база спочатку збирає бітову карту адрес сторінок і вичитує їх послідовно (`Bitmap Heap Scan`). Через читання сторінок по порядку блоків сортування B-Tree втрачається, і PostgreSQL досортовує записи в оперативній пам'яті.

---

### 4. Магія реального API: додавання пагінації (`LIMIT 20 / LIMIT 50`)

У реальних додатках запити завжди виконуються з пагінацією:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM "Order"
WHERE "status" = 'PAID' AND "createdAt" >= NOW() - INTERVAL '7 days'
ORDER BY "createdAt" DESC 
LIMIT 50;
```

#### Результат планування з LIMIT:
```text
Limit  (cost=0.42..122.96 rows=50 width=94) (actual time=0.041..0.180 rows=50 loops=1)
  Buffers: shared hit=53
  ->  Index Scan Backward using "Order_status_createdAt_idx" on "Order"  (actual time=0.040..0.161 rows=50 loops=1)
        Index Cond: ((status = 'PAID'::text) AND ("createdAt" >= (now() - '7 days'::interval)))
        Buffers: shared hit=53
Execution Time: 0.239 ms
```

> [!IMPORTANT]
> **Ключовий прорив:**  
> 1. Вузол `Sort` **повністю зник**! Оскільки листки B-Tree індексу вже впорядковані за датою, база просто читає їх у зворотному напрямку (`Index Scan Backward`).
> 2. Загальний час скоротився з **32.59 мс до 0.239 мс — у ~136 разів швидше за baseline**!

## 🚫 Блок 4: Дослідження правила лівого префікса (Leftmost Prefix Rule)

Було перевірено поведінку бази, коли фільтр виконується **лише за датою**, без колонки `status`:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM "Order"
WHERE "createdAt" >= NOW() - INTERVAL '7 days'
ORDER BY "createdAt" DESC;
```

#### Результат:
```text
->  Parallel Seq Scan on "Order"  (Filter: ("createdAt" >= (now() - '7 days'::interval)))
      Rows Removed by Filter: 61493
      Buffers: shared hit=3272
Execution Time: 41.844 ms
```

### 🧠 Чому індекс було проігноровано?
Наш індекс побудований як `(status, createdAt)`. Дані в B-Tree впорядковані спочатку за статусом:
`('CANCELLED', date) ... ('PAID', date) ... ('PENDING', date) ... ('SHIPPED', date)`.

Записи за останні 7 днів розташовані не в одному місці, а розпорошені по різних незалежних гілках кожного статусу. Оптимізатор порахував вартість обходу всіх гілок і вирішив, що швидше прочитати всю таблицю послідовно через `Parallel Seq Scan`.

## ⚖️ Блок 5: Закон селективності (Selectivity) та кардинальності (Cardinality)

Під час тестування було виконано запит без обмеження за датою:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM "Order"
WHERE "status" = 'PAID'
ORDER BY "createdAt" DESC;
```

Незважаючи на те, що `status` є першою колонкою індексу, база повернулася до **`Parallel Seq Scan` (Execution Time: 98.72 ms, rows=49949)**.

```
       ┌──────────────────────────────────────────────────────────┐
       │   Загальний обсяг таблиці: 200 000 рядків                │
       └──────────────────────────────────────────────────────────┘
                  │
        Селективність 25% (49 949 рядків) > Tipping Point (~10%)
                  │
        ┌─────────┴───────────────────────────────────────────────┐
        ▼                                                         ▼
  [ Random I/O через B-Tree ]                             [ Sequential I/O ]
  50 000 хаотичних стрибків по диску ❌                Швидке паралельне читання блоків ✅
  (Повільніше, дорожче)                                (Обрано планувальником CBO)
```

### Чому так сталося?
1. **Низька кардинальність (Cardinality):** Колонка `status` має лише 4 унікальні значення.
2. **Низька селективність (Selectivity):** Статус `'PAID'` покриває **25% (чверть) усієї таблиці**.
3. **Точка зламу (Tipping Point):** Якщо запит вимагає більше $10\dots 15\%$ рядків таблиці, виконання 50 000 випадкових звернень до дисків/буферів (Random I/O) коштує набагато дорожче, ніж послідовне вичитування підряд (Sequential I/O).
4. **Рішення:** Якщо додати `LIMIT 20`, запит вимагатиме лише 20 рядків ($0.01\%$), і PostgreSQL миттєво обере `Index Scan Backward` за **0.127 мс**.

## ✂️ Блок 6: Часткові індекси (Partial Indexes) та кастомні міграції Prisma

### Проблема:
В e-commerce системі 95–99% замовлень мають фінальні статуси (`COMPLETED`, `CANCELLED`). Створювати індекс на всі 200 000 рядків заради черги необроблених замовлень (`PENDING`) нераціонально.

### Обмеження Prisma DSL:
Prisma не підтримує вираз `WHERE` всередині директиви `@@index` у файлі `schema.prisma`.

### Архітектурне рішення — кастомна міграція Prisma:
1. Згенеровано порожній шаблон міграції:
   ```bash
   npx prisma migrate dev --create-only --name add_partial_pending_orders_idx
   ```
2. У створений файл [migration.sql](file:///home/bohdan/MyProjects/test_projects/order-inventory-service/server/prisma/migrations/20260905171352_add_partial_pending_orders_idx/migration.sql) додано чистий DDL:
   ```sql
   -- Create Partial Index for PENDING orders
   CREATE INDEX "idx_orders_pending" ON "Order"("createdAt") WHERE "status" = 'PENDING';
   ```
3. Міграцію застосовано через `npx prisma migrate dev`.

---

### Порівняння фізичного розміру індексів у PostgreSQL:

```sql
SELECT 
    c.relname AS index_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS index_size,
    c.reltuples AS indexed_rows
FROM pg_class c
JOIN pg_index i ON c.oid = i.indexrelid
WHERE indrelid = '"Order"'::regclass;
```

| Назва індексу | Тип індексу | Кількість проіндексованих рядків | Фізичний розмір на диску | Економія пам'яті |
| :--- | :--- | :---: | :---: | :---: |
| **`Order_pkey`** | Первинний ключ (`id`) | 200 006 | **16 MB** | — |
| **`Order_status_createdAt_idx`** | Повний складений B-Tree | 200 006 | **6 632 KB (~6.5 MB)** | Базовий ($1\times$) |
| **`idx_orders_pending`** | **Частковий (WHERE status = 'PENDING')** | 49 964 | **1 112 KB (~1.1 MB)** | **~83% економії (у 6 разів менший!)** |

#### Перевірка в роботі:
При виконанні запиту `WHERE status = 'PENDING' AND createdAt >= NOW() - INTERVAL '7 days'` планувальник автоматично обрав саме `idx_orders_pending`, оскільки його дерево значно компактніше і потребує менше I/O операцій.

## 🎯 Відповіді на питання для самоперевірки та технічних інтерв'ю

### 1. Чому B-Tree є стандартом за замовчуванням у реляційних БД, а не Hash-індекс?
* **Hash-індекс** підтримує лише операції точної рівності `WHERE id = 'x'` за $\mathcal{O}(1)$. Він принципово не може виконувати діапазонний пошук (`>`, `<`, `BETWEEN`), пошук за шаблоном префікса (`LIKE 'abc%'`) або сортування (`ORDER BY`).
* **B-Tree ($B^+$ Tree)** зберігає ключі у відсортованому вигляді, а його листкові вузли зв'язані у двозв'язний список. Це дозволяє за $\mathcal{O}(\log N)$ знайти початкову точку діапазону (Index Seek), а далі просто крокувати по зв'язаному списку листків без повторного звернення до кореня дерева (Leaf Scan).

### 2. Чим відрізняються `Index Scan`, `Bitmap Index Scan` та `Index Only Scan`?
1. **`Index Scan`:** Прямий пошук по індексу. Знайшовши ключ, база відразу робить одиночне дискове звернення до таблиці (Heap) за рядком. Ідеально для точкового пошуку (1–20 рядків) або запитів з `LIMIT`.
2. **`Bitmap Index Scan`:** Двоетапний процес. Спочатку сканується індекс і формується бітова мапа номерів сторінок у пам'яті (`work_mem`), після чого сторінки вичитуються з таблиці послідовно (`Bitmap Heap Scan`). Це перетворює дорогий Random I/O на дешевий Sequential I/O.
3. **`Index Only Scan`:** Найшвидший варіант. Усі колонки з `SELECT`, `WHERE` та `ORDER BY` вже містяться в індексі. База взагалі не звертається до таблиці (Heap Fetches: 0), якщо сторінки підтверджені картою видимості (Visibility Map).

### 3. Що таке правило лівого префікса у складених індексах?
Складений індекс на поля `(A, B, C)` фізично впорядковує записи спочатку за `A`, потім за `B`, і наприкінці за `C`. Індекс може використовуватися пошуковим алгоритмом B-Tree **лише тоді, коли в запиті зафіксовано неперервний ланцюжок умов, починаючи з крайньої лівої колонки**:
* `WHERE A = 1` — працює (префікс A).
* `WHERE A = 1 AND B = 2` — працює (префікс A, B).
* `WHERE B = 2` або `WHERE C = 3` — **НЕ працює** (порушено лівий префікс, буде `Seq Scan`).
* `WHERE A = 1 AND C = 3` — `A` використовується для пошуку в дереві, а `C` перевіряється звичайним залишковим фільтром у пам'яті.

### 4. Чому наявність індексу не гарантує, що база даних його використає?
Оптимізатор PostgreSQL працює на основі розрахунку вартості (**Cost-Based Optimizer, CBO**). Якщо фільтр має низьку селективність і повертає понад $10\dots 15\%$ таблиці (як у нашому випадку зі `status = 'PAID'`, де повернулося 25% даних), випадковий доступ до 50 000 блоків через індекс (Random I/O) буде значно повільнішим за багатопотокове послідовне сканування всієї таблиці (`Parallel Seq Scan`).

### 5. У чому полягає «ціна індексів» (Write Penalty)?
Кожен додатковий індекс:
1. **Сповільнює `INSERT`:** під час створення 1 рядка база повинна фізично записати дані в таблицю плюс у кожне окреме B-Tree дерево на цій таблиці.
2. **Спричиняє B-Tree Page Split:** коли сторінка індексу (8 KB) переповнюється, база вимушена виділяти новий блок і переносити туди половину ключів, що породжує стрибки затримок (Latency Spikes).
3. **Блокує HOT-updates (Heap-Only Tuples):** якщо оновлюється колонка, яка входить до складу будь-якого індексу, PostgreSQL змушений оновлювати індексні покажчики замість швидкого перезапису в тому самому блоці.
4. **Витрачає RAM:** індекси витісняють корисні гарячі дані з кешу `shared_buffers`.
